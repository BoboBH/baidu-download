# 代码质量问题模式库

## 🚫 重复通知/操作模式

### 问题特征
- 同一个操作在代码的不同位置被调用
- 通常出现在if-else分支中
- 常见于：通知发送、日志记录、错误处理

### 检测方法
```bash
# 搜索重复的方法调用
grep -n "send_notification" src/
grep -n "logger.info.*完成" src/
```

### 避免策略
1. **统一入口原则**：相同功能只在一个地方调用
2. **重构时机**：扩展功能时立即重构，不要遗留
3. **代码审查**：检查是否有"if-else中的重复调用"

## 🔀 条件分支重复逻辑

### 问题特征
```python
# ❌ 错误模式
if message_type == 'baidupan':
    process_message()
    send_notification()  # 重复调用
elif message_type == 'pdf':
    process_message()
    send_notification()  # 重复调用

# ✅ 正确模式
process_message()
send_notification()  # 统一调用
```

### 检测关键词
- "为X类型添加通知" ❌
- "专门处理Y情况" ❌
- "通用逻辑" ✅
- "统一处理" ✅

## 📢 遗留的特定实现

### 常见场景
- 最初只支持一种类型，后来支持多种类型
- 添加了通用逻辑，但忘记删除特定实现
- 重构时只修改了新代码，旧代码没有清理

### 检查清单
- [ ] 添加通用逻辑后，是否删除了被替代的特定逻辑？
- [ ] 扩展功能时，是否审查了现有的if-else分支？
- [ ] 是否有功能相同但调用位置不同的代码？

## 🔄 代码演进最佳实践

### 扩展功能时的思考步骤
1. **识别模式**：这个功能是否与现有功能重复？
2. **查找通用逻辑**：是否已有统一的处理方式？
3. **重构优先**：先重构，再扩展
4. **清理遗留**：删除被新逻辑替代的旧代码

### 重构时机
- ✅ **最佳时机**：添加新功能时
- ✅ **好时机**：修复bug时
- ✅ **必须时机**：发现重复代码时
- ❌ **坏时机**：单独的重构项目（容易被忽略）

## 📝 代码审查提醒

### 提交代码前检查
- [ ] 是否有重复的函数调用？
- [ ] 是否有功能相同的if-else分支？
- [ ] 是否添加了通用逻辑但忘记删除旧逻辑？
- [ ] 是否有遗留的调试代码或临时方案？

### 重构意识
每次添加新功能时问自己：
1. 这个功能是否与现有功能重复？
2. 能否通过重构现有代码来实现？
3. 如果添加了通用逻辑，是否清理了旧代码？

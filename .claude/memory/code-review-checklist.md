# 代码修改检查清单

## 🔍 提交代码前强制检查

### 重复代码检查 (Critical)
- [ ] **搜索相同方法调用**：`grep -rn "send_notification\|logger.info.*完成\|send_private_message" src/`
- [ ] **检查if-else分支**：是否有功能相同但分别处理的分支？
- [ ] **审查新增逻辑**：是否与现有通用逻辑重复？

### 代码演进检查
- [ ] **添加通用逻辑时**：是否删除了被替代的特定实现？
- [ ] **扩展功能时**：是否审查了现有的条件分支？
- [ ] **重构时**：是否所有调用点都已更新？

### 通知/日志统一性
- [ ] **webhook通知**：确保每条消息只发送一次
- [ ] **私信通知**：确保与webhook通知逻辑一致
- [ ] **错误日志**：使用统一的错误记录格式

## 🎯 常见反模式识别

### ❌ 反模式：特定类型重复处理
```python
# 错误：每种类型单独发送通知
if type == 'baidupan':
    process()
    send_notification()  # 第一次
elif type == 'pdf':
    process()
    send_notification()  # 第二次
```

### ✅ 正确模式：统一处理
```python
# 正确：统一处理所有类型
process()
send_notification()  # 只发送一次
```

## 🔄 重构时机提醒

### 强制重构时机
1. **添加通用逻辑后** → 立即删除被替代的特定实现
2. **发现重复代码** → 立即重构，不要"以后再说"
3. **扩展新功能** → 先审查现有代码能否复用

### 重构检查问题
- ✅ 这个新功能是否与现有功能重复？
- ✅ 能否通过修改现有代码实现，而不是添加新代码？
- ✅ 添加通用逻辑后，是否清理了旧代码？

## 📋 当前项目特定提醒

### 已知问题区域
1. **通知发送逻辑**：已修复重复通知，修改时注意保持统一性
2. **错误处理**：检查是否有重复的错误处理代码
3. **数据库操作**：确保数据库更新操作集中管理

### 扩展功能时的注意事项
- **添加新消息类型**：统一使用现有的通知和错误处理逻辑
- **修改文件处理**：检查是否已有通用的文件处理方法
- **数据库变更**：使用统一的数据访问层方法

## 🚨 修复后的验证步骤

### Webhook通知验证
- [ ] 检查日志：确认每个消息只发送一次通知
- [ ] 测试各种消息类型：确保没有重复通知
- [ ] 验证私信功能：确保私信通知正常工作

### 代码一致性验证  
- [ ] 运行完整测试：确保重构后功能正常
- [ ] 检查日志格式：确保错误信息格式统一
- [ ] 审查调用关系：确保所有调用点都正确更新
